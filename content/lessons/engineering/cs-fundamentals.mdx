Engineers reach for data structures and algorithms when a feature has a speed, memory, cost, or correctness problem. If all you hear is "we need to optimize," you cannot choose between shipping the slow version now and paying for the fast one.

Every term below is defined the first time it appears, and every idea carries the product decision it belongs to. A PM leaves able to name `n`, the metric at risk, and the appetite. **Optional details** panels use language-neutral pseudocode and worked traces to show how each mechanism operates. They remain closed by default.

This lesson builds technical judgment for product work:

- recognize the problem shape behind an engineering proposal
- understand why an engineer chooses one structure or algorithm
- connect that choice to speed, cost, correctness, and customer experience

Open **Optional details** when you want the implementation model. **Pseudocode** describes the steps without the punctuation and library rules of a programming language. It exposes pointer movement and array state, including the condition that stops each loop. Pseudocode does not compile into a working application.

Coding fluency needs a separate practice loop:

- implement each structure in a chosen language
- solve problems without copying the solution
- test edge cases and measure the result

A language-specific data structures and algorithms course is the right place for that work.

**Most production teams reuse the foundations.** A programming language's **standard library** is the collection of tested structures and functions shipped with that language.

- Most standard libraries provide dynamic arrays or lists, hash maps, sets, and sorting. Many also provide deques, heaps, priority queues, or binary-search helpers.
- Additional software packages may provide graph traversal, shortest-path, text-search, and optimization algorithms.
- Product engineers still write the feature-specific rules. A library cannot decide which login attempts belong in the fraud window, what counts as a booking conflict, which route cost matters, or which discount constraints the business accepts.
- Engineers implement a foundation from scratch when no suitable library exists, unusual performance constraints demand another design, or they are practising the mechanism in a coding course or interview.

The pseudocode teaches enough of the mechanism to review the choice and spot a broken assumption. Production code should use a maintained library when one fits, then add the product's rules around it.

Systems that span many machines (copying data for safety, keeping temporary copies of hot results, surviving a dead disk) belong to [system design](/learn/engineering/system-design). Here the scope is what data you hold, how you organize it, and what you do to it.

## Performance lands on the scoreboard

| Product area | What the user experiences | Business consequence |
|---|---|---|
| Checkout or paywall | The payment page takes too long, fails, or charges twice. | More buyers abandon the purchase, so conversion and revenue fall. Duplicate charges also create refunds and damage trust. |
| Search, feed, or lesson page | Results appear slowly, feel irrelevant, or fail to load. | New users take longer to reach value, which weakens activation. Returning users lose trust and visit less often, which hurts retention. |
| Admin dashboard | Filters take seconds to respond or reports show incorrect numbers. | Teams cannot finish routine work efficiently. Customers may reduce usage, refuse to buy more seats, or leave for a faster product. |
| Background work, such as exports or emails | The product accepts the request, but the file or email arrives late or never arrives. | Support tickets increase. If the company promised a delivery time in a service-level agreement (SLA), it may also breach that commitment. |
| Work the system repeats continuously | Servers repeatedly recalculate results or read more data than the feature needs. | The cloud provider charges for that unnecessary computing work, increasing operating cost and reducing profit margin. |

<Key>Algorithm choice is a product trade-off:</Key> ship a correct slow path now, or spend eng time on a fast path that protects conversion and cost. You name the outcome and the appetite. Eng picks the structure.

<PerformanceOutcomeDiagram />

Five factors sit behind every "which approach" argument:

- **Latency:** how long the user waits to see value
- **Throughput:** how much work the system handles each second
- **Cost:** processor time, memory, database reads, and data sent over the network
- **Freshness:** whether the answer must be current or can be slightly out of date
- **Risk:** how long the approach takes to build, operate, and debug

For instance, take Spotify search. The catalog kept growing, and checking every track title worked in a demo but became too slow for a real catalog. Search is a path into listening, so when it slows down, fewer users reach a song and start playing it. Engineers added an **index**, a separate lookup structure that finds matching tracks without checking the entire catalog, then ranked those matches so the most useful results appeared first.

## Complexity: how work grows

`n` is the size of the thing that matters for this feature: users, rows, lessons, cart lines, graph edges. **Big-O** describes the shape of the work as `n` grows, ignoring constants on purpose. It answers one question: at 10× or 100× the data, does the work stay flat, grow slowly, grow in step, or explode?

| Shape | Meaning | Product feel |
|---|---|---|
| O(1) | Flat, whatever `n` is | Lookup by id feels instant |
| O(log n) | Each step halves the problem | Indexed search stays fast at millions |
| O(n) | One pass over the data | Scan every lesson once |
| O(n log n) | Sort-shaped | Rank a feed of `n` items |
| O(n²) | Nested loops over `n` | Fine at 50, dead at 5,000 |
| O(2ⁿ), O(n!) | Try every combination | Only for tiny inputs, or with pruning |

<BigOGrowthDiagram />

**Space matters too.** A **cache** is a temporary copy of data you already computed, so the next request does not redo the work. Holding every user's timeline in that copy uses memory in proportion to how many users you store. That is O(n) space, and memory is a bill. Interview prep calls the choice between more CPU work and more memory the time/space trade-off. Product calls it "faster page, bigger instance."

**Admin "export all users."** At 200 users the O(n) export is a button. At 2 million it can cause an outage and fill the support backlog. Nothing about the code changed; `n` did. The fix is usually a background job plus an email link, not a faster button.

<TechDepth>

**Worst, average, amortized.** A hash map lookup is O(1) on average and O(n) in an unusually bad worst case. **Amortized cost** spreads an occasional expensive operation across many cheap ones. Appending to a dynamic array is O(1) amortized because most appends are cheap, while an occasional resize copies everything. Eng cares which cost a feature can tolerate. A payment request with a strict completion deadline cares about the worst case; a nightly job may only need the average.

**Why log n feels like magic.** Binary search throws away half the remaining data each step. A million sorted items resolve in about twenty steps. That is the whole reason indexed lookup beats scanning.

**Constants still exist.** An O(n²) approach with a tiny constant can beat O(n log n) at small `n`, which is why eng measures instead of arguing. Big-O compares growth, not milliseconds.

**The loop to watch for.** Users × users, or orders × line items, is O(n²) hiding in readable code. Coding agents produce these happily because the test data is small (see [engineering with AI](/learn/engineering/engineering-with-ai)).

</TechDepth>

A better brief names `n` today, `n` in twelve months, and what breaks first at 10×.

## The structures

A data structure organizes data so that some operations are cheap and others are expensive. Picking one is picking which operations your feature performs constantly.

Computer science uses the phrase **data structure** as an umbrella term, but two ideas sit underneath it:

- An **abstract data type (ADT)** defines behavior: which operations a program may perform and what those operations mean. A stack, for example, requires last in, first out access through `push`, `pop`, and `peek`.
- A **concrete data structure** defines storage: how the computer arranges the items in memory. Dynamic arrays and linked lists are concrete structures.

That distinction allows one structure to build another. A program can implement stack behavior with a dynamic array or a linked list. Calling a stack a "data structure" is normal shorthand; calling it an abstract data type is more precise.

The structures below fall into five groups. Read the group that matches the feature in front of you rather than working through all of them in order:

- **Everyday collections** hold items in a sequence: array, string, and linked list.
- **Keyed lookup** finds one record by a name you already hold: hash map and hash set.
- **Ordered access** decides which item comes out next: stack, queue and deque, and heap.
- **Hierarchies and networks** store relationships: tree, trie, graph, and union-find.
- **Space savers** trade exactness or completeness for memory: Bloom filter and LRU cache.

### Array and dynamic array

Start with the structure you already use whenever you write a numbered list.

An **array** stores items in a specific order. Each item receives a numbered position, called its **index**. Most programming languages start counting at zero, so the first item is at index `0`, the second at index `1`, and so on.

Imagine a row of numbered lockers. If you know that the item you need is in locker 4,000, you can go directly to locker 4,000. You do not need to open lockers 1 through 3,999 first. An array works the same way:

- **Read by position:** when the program already knows the index, it can jump directly to that item. Reading index 4,000 requires the same number of lookup steps as reading index 4. Big-O describes both as O(1), or constant time.
- **Find by value:** when the program knows only a value, such as the title `"Data structures and algorithms"`, it may need to inspect each item until it finds a match. In the worst case, it checks all `n` items, so the work is O(n).
- **Insert in the middle:** when order must remain intact, adding a new item at index 2 requires moving the old item at index 2 to index 3, the old item at index 3 to index 4, and so on. As the array grows, more items may need to move.
- **Add at the end:** a **dynamic array** can grow when it fills up. Most additions at the end are cheap. Occasionally the program creates a larger block of memory and copies the existing items into it.

<TechDepth>

An implementation tracks both **size**, the number of stored items, and **capacity**, the number of available positions. It preserves one rule: stored items occupy positions `0` through `size - 1`.

```text
PROCEDURE APPEND(items, size, capacity, newItem)
  IF size = capacity
    newCapacity ← MAXIMUM(1, capacity × 2)
    largerItems ← NEW ARRAY with newCapacity positions

    FOR position FROM 0 TO size - 1
      largerItems[position] ← items[position]

    items ← largerItems
    capacity ← newCapacity

  items[size] ← newItem
  size ← size + 1
  RETURN items, size, capacity
```

Suppose `["cart", "checkout"]` has size 2 and capacity 2. Appending `"receipt"` creates four positions, copies the first two values, and stores `"receipt"` at position 2. The next append uses position 3 without another resize. One expensive copy buys room for several cheap appends.

</TechDepth>

Consider a shopping cart. The cart keeps its line items in order so the interface can render the first item, second item, and third item. Reading a known position is easy. Finding the line item for product `ABC-123` still requires a scan unless the program also maintains a separate lookup from product ID to cart item.

Arrays fit product features where order matters:

- a course showing lessons in sequence
- products listed in a shopping cart
- a user's recent searches, newest first
- one page of search results

**Pagination** means dividing a long result set into smaller pages, such as 20 products at a time. The array usually holds the items for the current page. The database should still find those 20 rows efficiently before the application places them in the array.

That distinction prevents a common performance problem. The array itself is not a database. If the application loads 100,000 customer records into an array and checks them one by one on every page request, it repeats an O(n) scan for every visitor. A database index, explained later, lets the database locate the required rows first; the application then uses an array only for the small ordered result it needs to display.

**Product decision**

- **Used in:** ordered lesson lists, shopping-cart lines, image carousels, recent searches, and one page of search results.
- **Prefer an array when:** order matters, the feature often reads an item by position, and most additions happen at the end.
- **Avoid an array when:** the feature constantly inserts items near the beginning, removes items from the middle, or searches a large collection by value without a separate lookup.

### String

A **string** is an ordered sequence of characters: letters, numbers, spaces, punctuation, or symbols. `"Anadi"` is a string containing five characters. Because those characters sit in order, many string operations use the same techniques as arrays.

Picture letter tiles in a row. You can read the tile at a numbered position, compare two rows, remove spaces from either end, or search one row for a smaller sequence of tiles. A string gives a program those operations for text.

Common operations include:

- **Count:** calculate how many characters or words the string contains.
- **Search:** find a smaller sequence, called a **substring**, inside the larger string. For example, `"data"` is a substring of `"database"`.
- **Compare:** decide whether two strings should count as the same value.
- **Transform:** trim spaces, change letter casing, split a sentence, or join several strings.

Account signup makes this problem visible. A customer enters `Anadi@example.com ` with a capital letter and a space at the end. The same customer later enters `anadi@example.com`. A literal comparison treats those inputs as different strings. **Normalization** means applying agreed rules, such as removing surrounding spaces and converting email letters to lowercase, before comparison.

The product consequence is concrete: missing normalization can create duplicate accounts, split purchase history between identities, and lock a customer out of data they already own.

**Product decision**

- **Used in:** names, email addresses, search queries, URLs, messages, coupon codes, document text, and imported CSV fields.
- **Prefer string operations when:** the feature must validate, compare, search, split, or display human-readable text.
- **Avoid treating raw strings as final identity when:** casing, spaces, accents, phone-number formats, or aliases can make the same real-world value look different. Normalize first and keep a stable internal ID.

<TechDepth>

**Characters are not always one byte.** Unicode is the standard computers use to represent writing systems and symbols. Some visible characters, including many emoji, use multiple underlying code units. Code that assumes one visible character equals one byte can cut text incorrectly or miscount a username.

Those questions are product rules before they are string algorithms: should search ignore capital letters? Are accents significant? Should `"résumé"` match `"resume"`? Can a user include emoji in a display name?

</TechDepth>

### Linked list

A **linked list** stores each item in a separate container called a **node**. Each node holds the value and a link, or pointer, to the next node. A **doubly linked list** adds a second pointer to the previous node.

Picture a scavenger hunt. Each clue tells you where to find the next clue. You cannot jump straight to clue 4,000 because only clue 3,999 contains its location. Starting from the first node and reaching the 4,000th therefore requires O(n) steps.

The trade-off changes when you already hold the node you need:

- **Insert:** connect the previous node to the new node, then connect the new node to the next one.
- **Delete:** connect the surrounding nodes to each other, bypassing the deleted node.
- **Read by position:** start at one end and follow links until you reach that position.

<TechDepth>

The implementation changes links rather than shifting later values. It preserves one rule: following `next` from a node reaches the item that comes after it.

```text
PROCEDURE INSERT_AFTER(currentNode, newValue)
  newNode ← NODE containing newValue
  newNode.next ← currentNode.next
  currentNode.next ← newNode

PROCEDURE REMOVE_AFTER(currentNode)
  nodeToRemove ← currentNode.next
  currentNode.next ← nodeToRemove.next
  RETURN nodeToRemove.value
```

Start with `Edit A → Edit B → Edit C`. To insert `Edit X` after `Edit B`, point `Edit X` at `Edit C`, then point `Edit B` at `Edit X`. The result is `A → B → X → C`. Only two links change. The program must already hold the node for `Edit B`; finding that node from the beginning still takes a scan.

</TechDepth>

A design tool's undo history shows the benefit. Each edit can point to the edit before and after it. Undo moves one link backward; redo moves one link forward. The tool does not need to shift every later edit when it adds a new action.

Arrays still often read faster on real hardware because their items usually occupy one continuous block of memory. A linked list scatters nodes around memory, so the processor has to follow each pointer. Better Big-O for insertion does not guarantee a faster feature if the product mostly reads the list.

**Product decision**

- **Used in:** undo and redo history, browser navigation internals, music playlists that support frequent reordering, and the recency order inside an LRU cache.
- **Prefer a linked list when:** the program already holds the node to change and frequently inserts or removes nearby items without needing numbered access.
- **Avoid a linked list when:** the feature often asks for "item 4,000," scans the full collection, or benefits from compact memory. An array is usually simpler and faster for ordinary product lists.

### Hash map and hash set

A hash map is easier to understand when you compare it with an array.

**An array is a row of numbered shelves**

```text
Position 0 → Apple
Position 1 → Banana
Position 2 → Mango
```

If the program asks for position `2`, it goes directly to Mango. If it asks for Banana without knowing the position, it may need to check Apple first and Banana second.

**A hash map is a cabinet of labelled drawers**

```text
"apple"  → ₹100
"banana" → ₹40
"mango"  → ₹80
```

Each label is called a **key**. The information stored under that label is the **value**. Asking for the key `"banana"` takes the program directly to the value `₹40`; it does not check Apple and Mango first.

Now connect that simple model to a product feature.

**Customer-profile lookup**

An array could store profiles in order:

```text
Position 0 → Anadi's profile
Position 1 → Priya's profile
Position 2 → Rahul's profile
```

The application knows the customer ID `user-9281`, not the numbered position. It may have to check profiles until it finds the matching ID.

A hash map stores each profile under its customer ID:

```text
"user-9281" → Anadi's profile
"user-1042" → Priya's profile
"user-7814" → Rahul's profile
```

The application asks for `"user-9281"` and goes directly to Anadi's profile. A **hash map** therefore stores key-to-value pairs for fast lookup by a known key.

The word "directly" hides the important mechanism. The map does not scan its keys to discover where `"user-9281"` sits. A **hash function** runs the same calculation on that key during storage and lookup:

```text
hash("user-9281") → bucket 5
```

When the application stores the profile, the calculation sends it to bucket 5. When the application requests the profile, the same calculation sends the lookup to bucket 5. The map jumps to that bucket instead of checking buckets 0 through 4. That fixed amount of work gives a hash map O(1) lookup on average.

<TechDepth>

The map stores a short list of entries inside each bucket because different keys can land in the same bucket. Lookup preserves one rule: run the same hash calculation used during storage, then compare keys only inside the selected bucket.

```text
FUNCTION GET(map, key)
  bucketNumber ← HASH(key) MODULO map.numberOfBuckets

  FOR EACH entry IN map.buckets[bucketNumber]
    IF entry.key = key
      RETURN entry.value

  RETURN NOT_FOUND

PROCEDURE PUT(map, key, value)
  bucketNumber ← HASH(key) MODULO map.numberOfBuckets

  FOR EACH entry IN map.buckets[bucketNumber]
    IF entry.key = key
      entry.value ← value
      RETURN

  ADD (key, value) TO map.buckets[bucketNumber]
```

Suppose both `"user-9281"` and `"user-5555"` land in bucket 5. `GET("user-9281")` jumps to bucket 5, compares the one or two keys there, and returns the matching profile. It does not scan every customer. Too many entries in one bucket make lookup slower, which is why the map creates more buckets as it fills.

</TechDepth>

A **hash set** keeps only the keys, without a separate value. It answers a simpler question: "Have we already seen this?" For example, a waitlist can place each normalized email address in a set and reject a duplicate signup.

That difference powers several familiar features:

- **Session lookup:** find the stored sign-in state for a customer using its unique session ID.
- **Feature flag:** find whether a named feature is enabled for this customer.
- **Deduplication:** use a set to reject an email or imported row already seen.
- **Counting:** store a count under each event name, such as `lesson_started → 418`.
- **Plan or permission check:** answer whether the customer has access to a particular paid plan or protected action.

The product stake is response time and correctness. A keyed lookup keeps a profile page fast; a set prevents duplicate invitations, charges, or analytics events.

**Product decision**

- **Used in:** user ID to profile lookup, session storage, feature flags, shopping-cart items keyed by product ID, event counts, deduplication, and permission checks.
- **Prefer a hash map when:** the feature knows a unique key and needs to retrieve or update the matching value quickly.
- **Prefer a hash set when:** the feature only needs to answer "has this appeared?" or enforce uniqueness.
- **Avoid either one when:** customers need values in sorted order, need range queries such as dates between Monday and Friday, or do not have a stable key.

<TechDepth>

**Collisions explain "on average."** Two different keys can produce the same bucket number. That event is a **collision**. The map resolves collisions by keeping several entries in a bucket or checking nearby buckets. A healthy map has few entries to check in each bucket, so lookup remains O(1) on average. If all `n` keys collide, lookup falls to O(n) in the worst case.

**Resizing.** As buckets fill, collisions become more frequent. The map eventually creates more buckets and redistributes its entries, a process called **rehashing**. Most lookups remain cheap, but a resize can make one operation take longer than usual.

**What maps cannot do.** Order. "Give me items 50 to 60 sorted by title" wants a sorted structure or an ordered index, not a hash map. This is exactly why databases offer both hash indexes and tree indexes.

</TechDepth>

### Stack

A **stack** allows work at one end only. Adding an item is called **push**; removing the newest item is called **pop**. This produces last in, first out order.

Those rules define the behavior, not the storage. A dynamic array can implement a stack by adding and removing items only at its end. The array supplies the storage; the stack supplies the access rule.

Picture stacking trays in a cafeteria. Staff place each clean tray on top. The next customer takes the top tray, so the last tray added is the first one removed.

<TechDepth>

A dynamic array can implement the rule by treating its last item as the top. Push appends; pop reads and removes the last position.

```text
PROCEDURE PUSH(stack, item)
  APPEND item TO stack.items

FUNCTION POP(stack)
  IF stack.items IS EMPTY
    RETURN EMPTY

  topPosition ← LENGTH(stack.items) - 1
  item ← stack.items[topPosition]
  REMOVE item AT topPosition
  RETURN item
```

For browser history, pushing `Home`, then `Search`, then `Product` produces `[Home, Search, Product]`. Pop returns `Product`; the remaining top is `Search`. The program never removes `Home` while newer pages remain above it.

</TechDepth>

Browser navigation uses this shape:

1. Opening a new page pushes the previous page onto the history stack.
2. Pressing Back pops the most recent page.
3. Pressing Back again reveals the page before that.

Stacks also support undo history, closing nested dialogs in reverse order, and reading nested formats such as JSON or HTML. A parser is code that turns raw text into a structure the application can understand. It uses a stack to remember which bracket or tag still needs to close.

**Product decision**

- **Used in:** browser Back, undo, nested modal dismissal, spreadsheet formula evaluation, and checking whether brackets or HTML tags close correctly.
- **Prefer a stack when:** the most recent unfinished action must complete or reverse first.
- **Avoid a stack when:** work must be processed in arrival order, by urgency, or by an arbitrary ID. Those requirements point to a queue, priority queue, or map.

<TechDepth>

A **monotonic stack** keeps its values consistently increasing or decreasing. When a new value violates that order, the algorithm removes values until the order returns. That pattern answers questions such as "which later day first had a higher price?" in one pass instead of comparing every day with every later day.

</TechDepth>

### Queue and deque

A **queue** accepts new items at the back and removes old items from the front. This produces first in, first out order, like customers waiting at a checkout.

Customers join the back of a checkout line, and the cashier serves the person at the front. A new arrival does not normally move ahead of someone who has already waited.

A large account export can take several minutes. Making the customer hold the page open until it finishes creates timeouts and repeated clicks. A queue separates acceptance from completion:

1. The customer clicks **Export**.
2. The application places an export job at the back of the queue.
3. A **worker**, a program that processes queued jobs, takes the oldest job.
4. The product emails a download link when the file is ready.

The customer gets immediate confirmation while the server does expensive work separately. The same pattern handles emails, notifications, video processing, and print jobs.

A **deque**, pronounced "deck," is a double-ended queue. It adds and removes items at either end. One use is a **sliding window**, a moving group such as "events from the last five minutes." As time moves forward, new events enter one end and expired events leave the other.

<TechDepth>

A queue implementation keeps a **front position**, the index of the next item to remove. It does not shift every remaining item after each removal.

```text
PROCEDURE ENQUEUE(queue, item)
  APPEND item TO queue.items

FUNCTION DEQUEUE(queue)
  IF queue.frontPosition = LENGTH(queue.items)
    RETURN EMPTY

  item ← queue.items[queue.frontPosition]
  queue.frontPosition ← queue.frontPosition + 1
  RETURN item
```

If three export jobs arrive as `[Export A, Export B, Export C]`, the front position starts at `0`. The first dequeue returns `Export A` and moves the front to `1`; the next returns `Export B`. A production queue may reuse empty positions with a circular array, but its arrival-order rule stays the same.

</TechDepth>

**Product decision**

- **Used in:** email delivery, account exports, video processing, notification delivery, support-work assignment, and recent-event windows.
- **Prefer a queue when:** the customer should receive immediate acknowledgement while slower work finishes later, or fairness requires older work to run first.
- **Prefer a deque when:** the algorithm must add and remove data at both ends, such as maintaining events inside a moving time window.
- **Avoid a basic queue when:** one urgent job must jump ahead, the customer needs an immediate result, or jobs depend on one another. Use priorities, synchronous processing, or dependency tracking instead.

<QueueStackDiagram />

<TechDepth>

**Backpressure** occurs when customers or services add work faster than workers complete it. The queue grows, completion takes longer, and old jobs may expire.

The response depends on the product promise:

- **Rate limit:** temporarily reject or slow new requests.
- **Batch:** process several similar jobs together to reduce repeated work.
- **Set expectations:** show the customer's position or promise an email instead of an immediate result.
- **Add workers:** pay for more computing capacity to drain the queue faster.

</TechDepth>

### Heap and priority queue

A **priority queue** returns the most important item next instead of the oldest item. A **heap** is the tree-shaped data structure commonly used to implement that rule. It keeps only enough order to identify the highest- or lowest-priority item; it does not fully sort everything.

A hospital triage desk does not always treat the person who arrived first. Staff identify the patient with the most urgent need and treat that patient next. A heap keeps the next highest-priority item available without arranging every waiting item into a complete order.

Consider a support product holding 100,000 open tickets while displaying only the ten most urgent. Sorting every ticket whenever an agent opens the page repeats work the interface never uses. A heap keeps the next most urgent ticket easy to retrieve:

- Looking at the highest-priority item costs O(1).
- Adding a ticket costs O(log n).
- Removing the highest-priority ticket costs O(log n).

Priority queues also run scheduled timers, select trending content, and combine several already-sorted result streams. The product question is whether customers need the full ranking or only the first few results.

<TechDepth>

A **max-heap** stores the greatest priority at array position `0`. For every other position, the parent sits at `FLOOR((position - 1) ÷ 2)`. The implementation preserves one rule: every parent has priority greater than or equal to its children.

```text
PROCEDURE ADD(heap, ticket)
  APPEND ticket TO heap
  position ← LENGTH(heap) - 1

  WHILE position > 0
    parent ← FLOOR((position - 1) ÷ 2)
    IF heap[parent].priority ≥ heap[position].priority
      STOP
    SWAP heap[parent] WITH heap[position]
    position ← parent

FUNCTION REMOVE_HIGHEST(heap)
  IF LENGTH(heap) = 1
    RETURN REMOVE_LAST(heap)

  highest ← heap[0]
  heap[0] ← REMOVE_LAST(heap)
  position ← 0

  WHILE position HAS A CHILD
    largerChild ← CHILD WITH GREATER PRIORITY
    IF heap[position].priority ≥ heap[largerChild].priority
      STOP
    SWAP heap[position] WITH heap[largerChild]
    position ← largerChild

  RETURN highest
```

Suppose ticket priorities are stored as `[90, 70, 50]`. Adding priority `80` first places it at the end: `[90, 70, 50, 80]`. It exceeds its parent `70`, so the heap swaps them and becomes `[90, 80, 50, 70]`. The highest priority remains at position `0`; the rest need not form a complete ranking.

</TechDepth>

**Product decision**

- **Used in:** urgent-ticket routing, scheduled notifications, top-ten leaderboards, trending content, delivery dispatch, and selecting the next task by deadline.
- **Prefer a heap when:** the product repeatedly needs the highest-, lowest-, earliest-, or latest-priority item but does not need every item fully sorted.
- **Avoid a heap when:** customers need arbitrary lookup by ID, the entire list in exact order, or frequent searches for items that are not at the top.

### Tree, BST, and balanced tree

A **tree** represents a hierarchy. The top node is the **root**. A node below another node is its **child**, and the node above it is its **parent**. A node with no children is a **leaf**. **Depth** counts how far a node sits below the root; **fan-out** counts how many children a node has.

A family tree starts with one person or couple and branches into children, grandchildren, and later generations. Each downward step adds depth. The same branching shape describes folders and subfolders.

A course provides a familiar example: it has sections, each section has lessons, and each lesson may have exercises. That hierarchy is a tree. File folders, threaded comments, product categories, and company reporting lines use the same shape.

A **binary tree** allows each node to have at most two children. A **binary search tree (BST)** adds an ordering rule: values smaller than the current node go left; larger values go right. Following that rule discards half of a balanced tree at each step, making lookup, insertion, and deletion O(log n).

A badly shaped tree can become a long chain, which makes those operations O(n). A **balanced tree**, such as an AVL or red-black tree, moves nodes after updates to keep its height under control.

The shape creates product constraints:

- A comment thread with extreme depth becomes difficult to read and query.
- A folder with thousands of direct children creates large menus and expensive permission checks.
- A category tree with several possible parents is no longer a tree; it has become a graph.

**Traversal** means visiting every node in a deliberate order:

- **In-order:** visit left, current, right. A BST produces sorted values this way.
- **Pre-order:** visit the parent before its children. This works for copying or saving a hierarchy.
- **Post-order:** visit children before their parent. This works for deleting a folder only after deleting its contents.
- **Level-order:** visit one depth at a time. A comment interface can use it to load the top levels before deep replies.

**Product decision**

- **Used in:** course outlines, file folders, product categories, threaded comments, organisation charts, menus, and sorted database indexes.
- **Prefer a general tree when:** each item has one clear parent and the feature needs to preserve or navigate that hierarchy.
- **Prefer a balanced search tree when:** values must stay sorted while the application frequently adds, removes, and searches them.
- **Avoid a tree when:** an item can have several parents, relationships form loops, or the feature mainly needs direct lookup by key. Those cases point to a graph or hash map.

### Trie

A **trie**, pronounced "try," is a tree that stores one character along each step of a path. Words sharing a beginning also share the same path. The beginning of a word is called its **prefix**.

Imagine a hallway where each door is labelled with the next letter. To find words beginning with `car`, walk through doors `c`, `a`, and `r`. Every room beyond that point represents a possible continuation, such as `car`, `care`, or `cart`.

Autocomplete makes the shared path concrete. A list storing `cat`, `car`, and `care` follows one path for `ca`, then branches. After a customer types `car`, the application reaches that path and returns every word below it. Lookup work depends on the number of typed characters rather than the total number of stored words.

<TechDepth>

Each trie node keeps a map from the next character to the next node. A marker records whether a complete word ends there.

```text
PROCEDURE INSERT(root, word)
  node ← root
  FOR EACH character IN word
    IF node.children DOES NOT CONTAIN character
      node.children[character] ← NEW TRIE NODE
    node ← node.children[character]
  node.endsWord ← TRUE

FUNCTION FIND_PREFIX(root, prefix)
  node ← root
  FOR EACH character IN prefix
    IF node.children DOES NOT CONTAIN character
      RETURN NOT_FOUND
    node ← node.children[character]
  RETURN node
```

After inserting `car`, `care`, and `cart`, all three words share the nodes `c → a → r`. `FIND_PREFIX("car")` walks three links and returns that final `r` node. The application then collects complete words below it. Adding more words does not lengthen the walk to the prefix.

</TechDepth>

Tries power search suggestions, tag pickers, contact search, and matching lists of blocked or protected terms. The trade-off is memory: shared prefixes save some duplication, but every character node and pointer still occupies space.

**Product decision**

- **Used in:** search autocomplete, contact suggestions, command palettes, spelling dictionaries, tag pickers, and matching domain-name or network-address prefixes.
- **Prefer a trie when:** customers search by the beginning of a word and the product must return suggestions after each typed character.
- **Avoid a trie when:** the collection is small, customers search by meaning or spelling similarity, or memory cost matters more than prefix speed. A sorted array, hash map, or full-text search system may fit better.

### Graph

A **graph** represents things and the relationships between them. Each thing is a **node**; each relationship is an **edge**. Unlike a tree, a graph allows several parents, two-way relationships, and **cycles**, where following links can return to the starting node.

A city map is a graph. Intersections are nodes and roads are edges. Several roads can reach one intersection, roads can work in both directions, and following several roads can bring you back to where you started.

LinkedIn provides a familiar graph. Members are nodes and connections are edges. One member can connect to hundreds of others, two members can share connections, and a chain of connections can loop back to its starting point.

Graphs power:

- follow and friendship networks
- recommendations such as "customers who completed this lesson also started that one"
- group and folder permissions
- package or task dependencies
- delivery routes and workflow states

<TechDepth>

An **adjacency list** implements the graph as a map. Each node maps to a list of its neighbours.

```text
PROCEDURE ADD_TWO_WAY_EDGE(graph, firstNode, secondNode)
  APPEND secondNode TO graph[firstNode]
  APPEND firstNode TO graph[secondNode]
```

If Maya belongs to `Design` and `Design` can open `Roadmap`, the map can hold `Maya → [Design]` and `Design → [Maya, Roadmap]`. Traversal algorithms read one neighbour list at a time. A social product stores existing connections instead of allocating space for every possible pair of members.

</TechDepth>

**Product decision**

- **Used in:** social connections, recommendation relationships, document permissions, dependency planning, fraud rings, delivery routes, and workflows that can branch or loop.
- **Prefer a graph when:** items can connect to several other items and the feature asks about reachability, paths, clusters, or dependencies.
- **Avoid a graph when:** every item has one parent, lookup is only by ID, or a simple ordered list answers the requirement. Trees, maps, and arrays are easier to build and operate for those cases.

<TechDepth>

An **adjacency matrix** stores a table containing every possible pair. It uses more memory than an adjacency list but answers "are these two nodes connected?" directly. A social network usually uses adjacency lists because every member connects to a tiny fraction of all members.

</TechDepth>

### Union-find (disjoint set)

**Union-find**, also called a **disjoint-set structure**, tracks which items belong to the same group. It performs two jobs:

- **Find:** return the group containing an item.
- **Union:** merge two groups after learning they belong together.

People at an event receive coloured wristbands showing their group. Finding a person's group means checking the wristband colour. Combining the blue and green groups means giving them one shared group identity instead of comparing every blue person with every green person.

Identity resolution shows why grouping matters. A customer signs up with a personal email, later uses a work email, and then buys through an Apple private relay address, which forwards messages without revealing the customer's main address. Rules may conclude that all three accounts represent one person. Union-find merges those records into one group without repeatedly comparing every account with every other account.

<TechDepth>

The structure gives each item a parent. A group's representative points to itself. `FIND` follows parent links to that representative; `UNION` joins one representative to another.

```text
FUNCTION FIND(parent, item)
  IF parent[item] ≠ item
    parent[item] ← FIND(parent, parent[item])
  RETURN parent[item]

PROCEDURE UNION(parent, firstItem, secondItem)
  firstGroup ← FIND(parent, firstItem)
  secondGroup ← FIND(parent, secondItem)

  IF firstGroup ≠ secondGroup
    parent[secondGroup] ← firstGroup
```

Start with `A → A`, `B → B`, and `C → C`, so each account represents its own group. `UNION(A, B)` changes B's representative to A. `UNION(B, C)` first finds that B belongs to A, then attaches C to A. A later `FIND(C)` returns A. The assignment inside `FIND` shortens future paths, a technique called **path compression**.

</TechDepth>

The same structure groups devices, joins computer-network connections, and detects whether adding a relationship would create a cycle. The product stake is a complete customer history without an O(n²) comparison across millions of records.

**Product decision**

- **Used in:** merging duplicate customer identities, grouping devices that belong together, connecting computers into networks, clustering records, and checking whether two items already share a group.
- **Prefer union-find when:** the application repeatedly merges groups and asks whether two items belong to the same connected group.
- **Avoid union-find when:** the feature must list the path between items, remove arbitrary relationships, explain why two records were grouped, or store rich relationship details. A graph with explicit edges is more suitable.

### Bloom filter

A **Bloom filter** is a memory-efficient structure that answers a limited membership question:

- **Definitely absent:** the item has not appeared.
- **Probably present:** the item may have appeared, so the application performs a slower, exact check.

Imagine a quick screening card with several boxes. Each known item marks a few boxes. If a new item needs a box that remains unmarked, it is definitely absent. If all its boxes are marked, the marks may belong to that item or may overlap with marks from other items, so the answer is only "probably present."

The second answer can be wrong. A **false positive** occurs when the filter reports "probably present" for an item that is absent. It never produces a false negative for an item added correctly.

A browser safety check provides one example. The browser checks a web address against a Bloom filter of known dangerous sites. A "definitely absent" answer avoids a network request. A "probably present" answer triggers an exact server check before showing a warning. The customer gets faster browsing while the second check prevents the probabilistic result from making the final security decision.

Bloom filters also help databases skip files that cannot contain a requested key. The product trade-off is less memory and fewer slow reads in exchange for occasional unnecessary follow-up checks.

**Product decision**

- **Used in:** browser checks for dangerous web addresses, database file lookup, large-scale deduplication checks, and avoiding expensive requests for records that are certainly absent.
- **Prefer a Bloom filter when:** a fast "definitely absent" answer can skip expensive work and the application can verify every "probably present" answer elsewhere.
- **Avoid a Bloom filter when:** a false positive could directly block a payment, deny access, delete data, or produce a final customer-visible decision. Use an exact set or database lookup for those decisions.

### LRU cache

A **cache** keeps a temporary copy of data so the application can reuse it instead of repeating slower work. A cache has limited room, so it needs an **eviction policy**, a rule for deciding which copy to remove.

**LRU** means least recently used. An LRU cache removes the item nobody has requested for the longest time. It usually combines:

- a hash map that finds a cached value quickly
- a doubly linked list that records usage order

A small desk can hold only five documents while a filing cabinet holds hundreds. Keep recently used documents on the desk. When a sixth document arrives, return the document untouched for the longest time to the cabinet. The desk is the cache; the filing cabinet remains the original source.

A phone image gallery makes the trade-off visible. The phone cannot keep every viewed product image in memory. An LRU image cache keeps recently viewed images ready and removes an image the customer has not viewed for a long time. Returning to the previous product feels instant; opening an old product downloads its image again.

The product trade-off has three parts:

- A larger cache uses more memory but avoids more repeated work.
- A smaller cache costs less memory but removes useful copies sooner.
- The **hit rate**, the percentage of requests found in the cache, measures whether that memory is buying enough speed.

**Product decision**

- **Used in:** mobile image caches, recently viewed product data, browser resources, database query results, and signed-in session data.
- **Prefer an LRU cache when:** recent use predicts near-future use, repeated computation or download is expensive, and a missed lookup can safely fall back to the original source.
- **Avoid an LRU cache when:** every item must remain available, stale data could cause a wrong charge or permission decision, or usage recency does not predict what customers will request next.

### Which operations stay cheap

Use this table after the explanations above. "Known" means the program already holds the required index, key, or node; finding that reference may carry a separate cost.

| Structure | Fast operation | Expensive operation | Choose it when |
|---|---|---|---|
| Array | Read a known position in O(1); append usually costs O(1). | Finding a value or changing the middle costs O(n) because the program scans or shifts items. | The feature needs ordered items and usually reads by position. |
| Linked list | Insert or delete in O(1) after reaching the correct node. | Reaching an arbitrary position costs O(n) because each link must be followed. | The feature changes known positions more often than it jumps to numbered positions. |
| Hash map or set | Find, add, or remove a key in O(1) on average. | Finding by an unkeyed value still costs O(n), and maintaining sorted order is not supported. | The feature repeatedly asks "give me this ID" or "have we seen this value?" |
| Balanced binary search tree | Find, insert, or delete a sorted key in O(log n). | It carries rebalancing and pointer overhead that a simple array does not need. | The feature needs both fast updates and results kept in sorted order. |
| Heap | Read the highest- or lowest-priority item in O(1); add or remove it in O(log n). | Finding an arbitrary item costs O(n), and the rest of the structure is not fully sorted. | The feature needs the next best item or the top few items. |
| Trie | Find a word or prefix in time proportional to the word's length. | It can consume substantial memory because characters become nodes and links. | The feature searches by prefix, such as autocomplete. |
| Union-find | Check or merge groups in near-constant time. | It does not list relationships or support arbitrary group deletion well. | The feature repeatedly asks whether two records belong to the same group. |

## Worked algorithm patterns

The five families below match the five groups in the map. Each algorithm explains the product shape and decision first. Its **Optional details** panel shows how the algorithm moves through data and why the implementation saves work.

### Moving through ordered data

These four algorithms all avoid rescanning data the program has already examined. Sorted order or a moving boundary tells each one which items it can skip, which keeps a response time interactive as history, customers, or bookings grow.

#### Two pointers

Two pointers avoid restarting a scan when sorted order tells the algorithm which values can no longer match.

A **pointer** is a marker showing the item the algorithm is looking at now. The two-pointer pattern uses two markers. Each marker can sit in a different list, or both can sit at different positions in one list.

Consider a product importing contacts. It must find emails that already belong to an existing customer.

**Uploaded contacts**

```text
anadi@example.com
maya@example.com
ravi@example.com
```

**Existing customers**

```text
ben@example.com
maya@example.com
zoya@example.com
```

Both lists are in alphabetical order. Put one pointer at the first email in each list:

<TechDepth>

```text
FUNCTION FIND_DUPLICATES(uploaded, existing)
  uploadPosition ← 0
  existingPosition ← 0
  duplicates ← EMPTY LIST

  WHILE uploadPosition < LENGTH(uploaded)
        AND existingPosition < LENGTH(existing)
    uploadEmail ← uploaded[uploadPosition]
    existingEmail ← existing[existingPosition]

    IF uploadEmail = existingEmail
      APPEND uploadEmail TO duplicates
      uploadPosition ← uploadPosition + 1
      existingPosition ← existingPosition + 1
    ELSE IF uploadEmail COMES BEFORE existingEmail
      uploadPosition ← uploadPosition + 1
    ELSE
      existingPosition ← existingPosition + 1

  RETURN duplicates
```

The implementation preserves one rule: everything before either pointer has already been resolved. Sorted order proves which pointer can move without hiding a future match.

</TechDepth>

| Step | Uploaded pointer | Existing pointer | Decision |
|---|---|---|---|
| 1 | `anadi@...` | `ben@...` | `anadi` comes before `ben`, so move only the uploaded pointer. Every remaining existing email comes after `ben`, so none can equal `anadi`. |
| 2 | `maya@...` | `ben@...` | `ben` comes before `maya`, so move only the existing pointer. |
| 3 | `maya@...` | `maya@...` | The emails match. Mark `maya@...` as a duplicate, then move both pointers. |
| 4 | `ravi@...` | `zoya@...` | `ravi` comes before `zoya`, so move the uploaded pointer. The uploaded list is now finished. |

The alphabetical order makes each move safe. Once `anadi` comes before the current existing email `ben`, no later existing email can be `anadi`. The importer never needs to move backward.

With three uploaded contacts and three existing customers:

- Comparing every possible pair can require `3 × 3 = 9` comparisons.
- Two pointers move through at most `3 + 3 = 6` positions.

At one million contacts in each list, comparing every pair could mean one trillion comparisons. Two pointers need at most about two million moves.

**Where products use it**

- **Duplicate detection:** find contacts, customers, or transactions appearing in both sorted lists.
- **Merging:** combine two sorted result pages into one sorted result.
- **Finding a pair:** place one pointer at each end of sorted prices such as `[£10, £20, £35, £50]`. For a £60 target, the first comparison finds `£10 + £50`.

**Product decision**

- **Prefer it when:** the data is already sorted, or sorting it once supports enough later work to justify the cost.
- **Avoid it when:** the data has no useful order and a comparison does not tell you which items can be discarded. A hash set may answer a one-off duplicate check more directly.

#### Sliding window

Slide a picture frame across a long timeline. The frame shows only the events inside it. New events enter on the right; old events leave on the left.

For instance, a fraud rule locks an account after three failed logins within five minutes. It adds each new failure to the current range and removes failures that have become too old.

<TechDepth>

The implementation stores timestamps in a deque from oldest to newest. It preserves one rule: after cleanup, every timestamp in the deque falls inside the current five-minute window.

```text
PROCEDURE RECORD_FAILED_LOGIN(recentFailures, currentTime)
  APPEND currentTime TO BACK OF recentFailures
  windowStart ← currentTime - 5 MINUTES

  WHILE recentFailures IS NOT EMPTY
        AND FRONT(recentFailures) < windowStart
    REMOVE FRONT OF recentFailures

  IF LENGTH(recentFailures) ≥ 3
    LOCK ACCOUNT
```

Suppose failures arrive at `10:00`, `10:03`, and `10:06`:

| Current failure | Deque before cleanup | Cleanup | Result |
|---|---|---|---|
| 10:00 | `[10:00]` | Nothing is older than 09:55. | One recent failure. |
| 10:03 | `[10:00, 10:03]` | Nothing is older than 09:58. | Two recent failures. |
| 10:06 | `[10:00, 10:03, 10:06]` | Remove 10:00 because it is older than 10:01. | Two recent failures, so the account stays open. |
| 10:07 | `[10:03, 10:06, 10:07]` | Nothing is older than 10:02. | Three recent failures, so the rule locks the account. |

Each failure enters and leaves the deque once, so processing `n` failures takes O(n) work across the full timeline. The rule does not reread account history after each attempt.

</TechDepth>

**Product decision**

- **Used in:** fraud rules, rate limits, activity streaks, and continuous ranges inside text or event history.
- **Prefer it when:** the requirement says "during the last N minutes," "inside this range," or "longest continuous sequence."
- **Avoid it when:** the relevant items are scattered rather than contiguous, or each query asks for an unrelated range.

#### Prefix sums

A bank statement prints a running balance beside every transaction. To calculate activity between two points, subtract the running total before the range from the running total at its end.

For instance, daily spend `[£4, £7, £2]` produces cumulative totals `[£4, £11, £13]`. Spend from day two through day three is `£13 - £4 = £9`.

<TechDepth>

The implementation builds an extra array whose first value is zero. It preserves one rule: `prefix[position]` equals the total of all values before that position.

```text
FUNCTION BUILD_PREFIX_SUMS(values)
  prefix ← ARRAY containing one value: 0

  FOR EACH value IN values
    APPEND LAST(prefix) + value TO prefix

  RETURN prefix

FUNCTION RANGE_TOTAL(prefix, startPosition, endPosition)
  RETURN prefix[endPosition + 1] - prefix[startPosition]
```

Daily spend `[£4, £7, £2]` creates `[£0, £4, £11, £13]`. Day two through day three uses positions 1 through 2: `prefix[3] - prefix[1] = £13 - £4 = £9`. Building the array costs O(n) once; every later range total costs O(1).

</TechDepth>

**Product decision**

- **Used in:** spend reports, cumulative usage, inventory movement, and analytics over date ranges.
- **Prefer it when:** values stay stable while the product asks many total-between-two-points questions.
- **Avoid it when:** values change constantly, because one early change may require updating every later cumulative total.

#### Intervals

Draw meetings as bars on a calendar. Two bars overlap when each starts before the other one ends.

For instance, a calendar compares each proposed booking with existing bookings before confirming it. The same interval representation lets the product merge overlapping busy periods.

<TechDepth>

For a single booking request, compare the proposed range with every existing booking:

```text
FUNCTION HAS_CONFLICT(existingBookings, proposedBooking)
  FOR EACH booking IN existingBookings
    IF proposedBooking.start < booking.end
       AND booking.start < proposedBooking.end
      RETURN TRUE

  RETURN FALSE
```

An existing booking from 10:00 to 11:00 conflicts with a proposed 10:30 to 11:30 booking because `10:30 < 11:00` and `10:00 < 11:30`. A proposed 11:00 to 12:00 booking does not conflict when the product allows one booking to start at the exact time another ends.

Merging many busy periods starts by sorting them by start time. The algorithm preserves one rule: the result contains merged, non-overlapping intervals in start-time order.

```text
FUNCTION MERGE_INTERVALS(intervals)
  SORT intervals BY start time
  merged ← EMPTY LIST

  FOR EACH current IN intervals
    IF merged IS EMPTY OR LAST(merged).end < current.start
      APPEND current TO merged
    ELSE
      LAST(merged).end ← MAXIMUM(LAST(merged).end, current.end)

  RETURN merged
```

`[10:00, 11:00]`, `[10:30, 11:30]`, and `[13:00, 14:00]` become `[10:00, 11:30]` and `[13:00, 14:00]`. Sorting costs O(n log n); the merge then scans once in O(n).

</TechDepth>

**Product decision**

- **Used in:** calendars, subscriptions, pricing validity, room allocation, and delivery windows.
- **Prefer it when:** each item has a start and end, such as a booking or delivery window.
- **Avoid it when:** the feature cares about isolated points rather than ranges.

### Ordering, selecting, and remembering

These algorithms decide what order the data should take, or which few items the product needs to show. Two structures already covered do the same job: a [heap](#heap-and-priority-queue) returns the top few items without a full ranking, and a [hash set](#hash-map-and-hash-set) remembers what the program has seen before.

#### Sorting

A **sorting algorithm** rearranges values into an order, such as newest first, lowest price first, or highest score first. A **comparison sort** decides order by comparing pairs of values. Efficient general-purpose comparison sorts usually cost O(n log n).

Arrange books on a shelf by title. Compare two books, place the earlier title first, and repeat until the shelf follows one order. The rule could instead use author, publication date, or height; the chosen rule changes the result.

<TechDepth>

**Merge sort** provides one concrete implementation. It divides the array until each piece holds one item, then merges sorted pieces. During each merge, the output preserves one rule: it always takes the smaller first unmerged value.

```text
FUNCTION MERGE_SORT(items)
  IF LENGTH(items) ≤ 1
    RETURN items

  middle ← FLOOR(LENGTH(items) ÷ 2)
  left ← MERGE_SORT(items BEFORE middle)
  right ← MERGE_SORT(items FROM middle onward)
  RETURN MERGE(left, right)

FUNCTION MERGE(left, right)
  result ← EMPTY LIST
  leftPosition ← 0
  rightPosition ← 0

  WHILE leftPosition < LENGTH(left)
        AND rightPosition < LENGTH(right)
    IF left[leftPosition] ≤ right[rightPosition]
      APPEND left[leftPosition] TO result
      leftPosition ← leftPosition + 1
    ELSE
      APPEND right[rightPosition] TO result
      rightPosition ← rightPosition + 1

  WHILE leftPosition < LENGTH(left)
    APPEND left[leftPosition] TO result
    leftPosition ← leftPosition + 1

  WHILE rightPosition < LENGTH(right)
    APPEND right[rightPosition] TO result
    rightPosition ← rightPosition + 1

  RETURN result
```

Scores `[42, 17, 31, 8]` split into `[42, 17]` and `[31, 8]`, then into single values. The merges produce `[17, 42]` and `[8, 31]`; the final merge produces `[8, 17, 31, 42]`. Each level processes all `n` items, and there are about `log n` levels, so the work is O(n log n).

</TechDepth>

Take a Learn homepage showing the ten most popular lessons this week. Product first defines **popular**: starts, completions, or a score combining both. Engineering then chooses how often to calculate that order.

| Approach | What it means | Suitable when | Product cost or risk |
|---|---|---|---|
| Sort on every page request | Recalculate the order whenever a customer opens the page. | The collection is small and customers need the newest answer. | Page latency and computing cost grow with both traffic and catalog size. |
| Keep only the top K in a heap | Track the best `K` items, such as the top ten, without fully ordering the rest. | The interface displays only a small leaderboard. | The team must still define when scores refresh; stale scores make "popular" feel false. |
| Precompute the ranking | Calculate order on a schedule and store the result for reuse. | Hourly or nightly freshness meets the product promise. | Customers may not see a sudden trend until the next calculation. |
| Maintain an ordered database index | Ask the database to keep values arranged by a chosen field as records change. | Many requests repeatedly need the same ordering or range. | Every write must also update the index, using storage and write capacity. |

The product decision is how current the ranking must be, how many items appear, and how much infrastructure cost that surface deserves.

#### Binary search

**Binary search** finds a value in sorted data by comparing with the middle and discarding half of the remaining possibilities. It can also find a boundary inside an ordered range of possible answers.

Finding a name in an unsorted pile of cards means checking cards one by one. Finding the same name in an alphabetized phone directory lets you open near the middle. If the target comes later alphabetically, you can discard the entire first half.

<TechDepth>

Binary search keeps two array positions around the remaining search area. It preserves one rule: if the target exists, it lies between `low` and `high`.

```text
FUNCTION BINARY_SEARCH(sortedItems, target)
  low ← 0
  high ← LENGTH(sortedItems) - 1

  WHILE low ≤ high
    middle ← FLOOR((low + high) ÷ 2)

    IF sortedItems[middle] = target
      RETURN middle
    ELSE IF sortedItems[middle] < target
      low ← middle + 1
    ELSE
      high ← middle - 1

  RETURN NOT_FOUND
```

Searching `[10, 20, 35, 50, 80]` for `50` first checks `35` at the middle. Since `50` is greater, the algorithm moves `low` past `35` and discards the first three positions. The next middle value is `50`, so it returns that position.

</TechDepth>

For instance, suppose uploads must finish within two seconds. The team wants the largest supported size between 1 MB and 100 MB:

| Test | Remaining sizes | Result | What remains |
|---|---|---|---|
| 1 | 1 to 100 MB | 50 MB takes 3 seconds, so it is too slow. | Keep 1 to 49 MB. |
| 2 | 1 to 49 MB | 25 MB takes 1.5 seconds, so it passes. | Keep 25 MB as the current answer and search 26 to 49 MB. |
| 3 | 26 to 49 MB | 37 MB takes 2.2 seconds, so it is too slow. | Keep 26 to 36 MB. |
| 4 | 26 to 36 MB | 31 MB takes 1.8 seconds, so it passes. | Search 32 to 36 MB. |
| 5 | 32 to 36 MB | 34 MB takes 2 seconds, so it passes. | Search 35 to 36 MB. |
| 6 | 35 to 36 MB | 35 MB takes 2.1 seconds, so it is too slow. | The largest passing size is 34 MB. |

<TechDepth>

The boundary version changes the response to a passing test. Instead of returning that size at once, it saves the size and searches the larger half for a better passing answer.

```text
FUNCTION LARGEST_PASSING_SIZE(smallest, largest)
  answer ← NONE
  low ← smallest
  high ← largest

  WHILE low ≤ high
    middle ← FLOOR((low + high) ÷ 2)

    IF UPLOAD_AT_SIZE(middle) MEETS TIME LIMIT
      answer ← middle
      low ← middle + 1
    ELSE
      high ← middle - 1

  RETURN answer
```

</TechDepth>

The search takes about seven tests for 100 possible sizes because each test removes half of the remaining range.

**Product decision**

- **Prefer binary search when:** the data is sorted, or the possible answers form a boundary where everything below passes and everything above fails.
- **Avoid binary search when:** results have no dependable order. Response-time tests also need repeated measurements because traffic and network conditions create noise.

#### Greedy selection

A **greedy algorithm** chooses the best available option now and does not revisit the choice. This approach is faster and simpler than exploring combinations, but it is correct only when the problem has the right mathematical structure.

Choose the option that looks best at each step, cross it off, and never revisit it. This saves the work of comparing complete combinations, but an attractive choice now can block a better result later.

A meeting scheduler is one case where the greedy choice works. Repeatedly choosing the meeting that finishes earliest leaves the most room for later meetings and maximizes the number that fit. The same strategy does not solve every pricing or resource problem.

<TechDepth>

```text
FUNCTION SELECT_MOST_MEETINGS(meetings)
  SORT meetings BY finish time
  selected ← EMPTY LIST
  lastFinish ← START OF DAY

  FOR EACH meeting IN meetings
    IF meeting.start ≥ lastFinish
      APPEND meeting TO selected
      lastFinish ← meeting.finish

  RETURN selected
```

Given meetings `A: 09:00-10:00`, `B: 09:30-11:30`, and `C: 10:00-11:00`, finish-time order is A, C, B. The algorithm chooses A, then C because C starts when A finishes. It rejects B because B overlaps the selected schedule. Choosing B first would fit only one meeting; the earliest-finish rule fits two.

</TechDepth>

An engineer saying "greedy works here" should be able to explain why the local choice cannot block a better final answer. Passing a few examples is not enough when the output controls money, eligibility, or capacity.

**Product decision**

- **Used in:** selecting non-overlapping meetings, compressing files by assigning shorter codes to common symbols, and making fast allocation choices where engineers have proven the greedy rule.
- **Prefer a greedy algorithm when:** the local choice has a clear proof, speed matters, and revisiting prior choices would add cost without improving the final answer.
- **Avoid a greedy algorithm when:** discounts, capacity, or dependencies interact in ways where today's best-looking choice can block tomorrow's better combination.

### Exploring combinations

The algorithms below build an answer out of smaller decisions. They matter when the product asks for the best combination or a valid one, and the number of possible combinations is too large to check exhaustively.

#### Recursion

**Recursion** solves a problem by calling the same procedure on a smaller version of that problem. It fits data that repeats its own shape, such as a folder containing more folders. Every unfinished call uses the **call stack**, the program's record of procedures that still need to finish.

Open a box containing smaller boxes. To count every object, use the same instruction on each box: count the loose objects, open every smaller box, and add its count. The instruction repeats until it reaches a box containing no more boxes.

Calculating a folder's size provides a recursive example. The calculation adds its files plus the sizes of every child folder. The same procedure calculates each child, so the code follows the tree naturally.

<TechDepth>

```text
FUNCTION FOLDER_SIZE(folder)
  total ← SUM OF sizes of files directly inside folder

  FOR EACH childFolder IN folder.childFolders
    total ← total + FOLDER_SIZE(childFolder)

  RETURN total
```

Suppose `Projects` contains a 5 MB file and a child folder named `Archive` containing 3 MB and 2 MB files. `FOLDER_SIZE(Archive)` returns 5 MB. The unfinished `Projects` call then adds its own 5 MB and returns 10 MB. The **base case** occurs when a folder has no child folders; its loop performs no recursive calls.

</TechDepth>

**Product decision**

- **Prefer recursion when:** the data repeats a nested shape, such as folders, comments, or organisational units, and the maximum depth is controlled.
- **Avoid plain recursion when:** the input can contain many nested levels, several paths repeat the same work, or the call stack could run out of room.

#### Memoization and dynamic programming

Recursion becomes expensive when several paths ask for the same smaller answer. **Memoization** stores each completed answer so a repeated request becomes a lookup. **Dynamic programming** plans the required smaller answers and builds the final answer from them. A **bottom-up** version fills a table from the smallest case to the largest instead of making recursive calls.

Memoization is the sticky-note version: write each solved answer down, and when the same question appears again, read the note instead of solving it again.

Dynamic programming is the worksheet version: complete it from the smallest known answers upward. Each new row uses answers already written above it, so the work and its order are predictable.

<RecursionToDpDiagram />

<TechDepth>

Consider a checkout choosing each discount offer at most once under a £10 budget. Each offer has a cost to the business and a customer value. A top-down memoized implementation asks whether to skip or take the current offer:

```text
FUNCTION BEST_VALUE(offers, position, remainingBudget, memo)
  IF position = LENGTH(offers)
    RETURN 0

  key ← (position, remainingBudget)
  IF memo CONTAINS key
    RETURN memo[key]

  skipValue ← BEST_VALUE(offers, position + 1, remainingBudget, memo)
  takeValue ← 0

  IF offers[position].cost ≤ remainingBudget
    takeValue ← offers[position].value
                + BEST_VALUE(
                    offers,
                    position + 1,
                    remainingBudget - offers[position].cost,
                    memo
                  )

  memo[key] ← MAXIMUM(skipValue, takeValue)
  RETURN memo[key]
```

The key stores both the next offer and the remaining budget because those two values define the smaller question. If several choice paths reach `(offer 3, £4 remaining)`, the function computes that answer once.

A bottom-up implementation stores the best value for every budget from £0 through £10:

```text
FUNCTION BEST_VALUE_BOTTOM_UP(offers, budget)
  best ← ARRAY OF budget + 1 ZEROS

  FOR EACH offer IN offers
    FOR available FROM budget DOWN TO offer.cost
      withoutOffer ← best[available]
      withOffer ← best[available - offer.cost] + offer.value
      best[available] ← MAXIMUM(withoutOffer, withOffer)

  RETURN best[budget]
```

Suppose one offer costs £6 and creates £8 of customer value, while another costs £4 and creates £5. After the first offer, `best[10]` is £8. Processing the second offer compares £8 with `best[6] + £5 = £13`, so the final answer combines both offers. The loop moves backward through budgets so it cannot reuse the same offer twice.

</TechDepth>

Common dynamic-programming families include:

- **Knapsack:** choose the most valuable combination that fits a fixed capacity or budget. This resembles selecting promotions under a discount cap.
- **Edit distance:** count the fewest character changes needed to turn one string into another. Document differences and fuzzy spelling matches use this shape.
- **Grid paths:** count or optimize routes through cells containing obstacles. Warehouse picking and game movement use related forms.
- **Coin change:** construct a target total from available denominations. Pricing bundles and discount combinations can have this shape.
- **Longest increasing subsequence:** find the longest ordered improvement inside a sequence. It can detect sustained growth hidden inside noisy measurements.

The phrase "exponential without memoization" means repeated work grows so quickly that the feature needs a strict input limit or stored intermediate answers before it can ship safely.

**Product decision**

- **Prefer dynamic programming when:** the feature asks for the best result and repeatedly encounters the same smaller questions.
- **Avoid dynamic programming when:** smaller questions do not repeat or storing every intermediate answer would consume more memory than the outcome deserves.

<TechDepth>

Dynamic programming fits when two properties hold:

- **Overlapping subproblems:** different routes through the problem ask for the same smaller answer.
- **Optimal substructure:** the best final answer can be built from best answers to smaller parts.

</TechDepth>

#### Backtracking

**Backtracking** builds one possible answer step by step. As soon as a partial answer breaks a rule, the algorithm abandons that branch and returns to the last choice point. That early exit is called **pruning** because it cuts away part of the search tree.

Solve a maze with a pencil. Follow one path until it reaches a dead end, return to the last junction, and try the next path. Marking the dead end prevents you from exploring an impossible route further.

A shift scheduler makes pruning useful. It assigns employees one at a time. If a partial schedule already gives someone overlapping shifts or exceeds their permitted hours, no completed version of that branch can work. The algorithm stops exploring it.

<TechDepth>

The implementation keeps a partial schedule and removes its last choice when that choice leads nowhere. It preserves one rule: every assignment already in the partial schedule satisfies all constraints.

```text
FUNCTION BUILD_SCHEDULE(shifts, position, partialSchedule)
  IF position = LENGTH(shifts)
    RETURN COPY OF partialSchedule

  currentShift ← shifts[position]

  FOR EACH employee IN currentShift.eligibleEmployees
    IF ASSIGNING employee WOULD NOT BREAK A RULE
      ADD (currentShift, employee) TO partialSchedule

      result ← BUILD_SCHEDULE(shifts, position + 1, partialSchedule)
      IF result EXISTS
        RETURN result

      REMOVE LAST ASSIGNMENT FROM partialSchedule

  RETURN NO_VALID_SCHEDULE
```

Suppose Priya and Mateo can cover morning and afternoon, but one person cannot cover both. The scheduler first assigns morning to Priya. If it later assigns afternoon to Priya, the rule fails before another recursive call. It tries Mateo instead. Removing the failed choice is the backtracking step.

</TechDepth>

Backtracking powers seat assignment, valid coupon combinations, and configuration tools with interacting constraints. The number of combinations can still grow exponentially. Product can reduce that cost by limiting party size, limiting how many promotions may combine, or accepting a good-enough answer after a time limit.

**Product decision**

- **Used in:** shift scheduling, seat assignment, valid promotion combinations, configuration tools, and puzzle-like constraint problems.
- **Prefer backtracking when:** the input is small enough to explore, rules can reject bad partial answers early, and the product needs a valid combination rather than a formula.
- **Avoid backtracking when:** the number of choices is large and unbounded or the customer needs a guaranteed instant answer. Reduce the choices, use an approximation, or move the work into a background job.

### Following relationships and dependencies

**Graph traversal** means visiting connected nodes in a deliberate order. All four algorithms below walk a [graph](#graph), and the requirement decides which one fits: the fewest relationships, any reachable path, a valid prerequisite order, or the lowest total cost. [Union-find](#union-find-disjoint-set) answers a fifth question, whether two items already share a group, without walking a path at all.

#### Breadth-first search

**Breadth-first search (BFS)** explores every node one edge away, then every node two edges away, and so on. Picture ripples spreading from a pebble. A queue preserves that layer-by-layer order.

<TechDepth>

```text
FUNCTION SHORTEST_HOPS(graph, start, target)
  queue ← QUEUE containing (start, 0)
  visited ← SET containing start

  WHILE queue IS NOT EMPTY
    node, distance ← DEQUEUE(queue)
    IF node = target
      RETURN distance

    FOR EACH neighbour IN graph[node]
      IF neighbour IS NOT IN visited
        ADD neighbour TO visited
        ENQUEUE (neighbour, distance + 1) INTO queue

  RETURN NOT_REACHABLE
```

For instance, a Google Drive permission graph may connect `Maya → Design group → Roadmap`. BFS starts with Maya at distance 0, then visits the Design group at distance 1 and Roadmap at distance 2. Marking nodes as visited prevents a membership cycle from trapping the search.

</TechDepth>

#### Depth-first search

**Depth-first search (DFS)** follows one path to its end before returning to the latest choice point. A call stack or explicit stack preserves the unfinished paths.

<TechDepth>

```text
FUNCTION CAN_REACH(graph, node, target, visited)
  IF node = target
    RETURN TRUE

  ADD node TO visited

  FOR EACH neighbour IN graph[node]
    IF neighbour IS NOT IN visited
      IF CAN_REACH(graph, neighbour, target, visited)
        RETURN TRUE

  RETURN FALSE
```

If Maya belongs to Design, Design belongs to Product, and Product can open Roadmap, DFS follows that chain until it reaches Roadmap. If the chain ends, the call returns and tries Design's next connection. DFS proves reachability, but it does not guarantee the fewest relationships.

</TechDepth>

#### Topological sort

**Topological sort** orders one-way dependencies so every prerequisite appears before the work that needs it. **In-degree** counts how many unfinished prerequisites point into a node.

<TechDepth>

```text
FUNCTION DEPENDENCY_ORDER(graph)
  inDegree ← MAP with 0 for every node

  FOR EACH node IN graph
    FOR EACH dependent IN graph[node]
      inDegree[dependent] ← inDegree[dependent] + 1

  ready ← QUEUE containing every node with inDegree 0
  order ← EMPTY LIST

  WHILE ready IS NOT EMPTY
    node ← DEQUEUE(ready)
    APPEND node TO order

    FOR EACH dependent IN graph[node]
      inDegree[dependent] ← inDegree[dependent] - 1
      IF inDegree[dependent] = 0
        ENQUEUE dependent INTO ready

  IF LENGTH(order) < NUMBER OF NODES
    RETURN CYCLE_FOUND
  RETURN order
```

For account migration, `Create account → Import data → Generate report`. Only account creation starts with zero prerequisites. Completing it makes import ready; completing import makes report generation ready. If import waits for report while report waits for import, no node becomes ready and the algorithm reports a cycle.

</TechDepth>

#### Dijkstra's algorithm

**Dijkstra's algorithm** finds the lowest-total-cost path when every edge weight is zero or greater. It stores the best known cost to each node and uses a min-heap to process the cheapest unfinished route next.

<TechDepth>

```text
FUNCTION LOWEST_COST(graph, start, target)
  distance ← MAP with INFINITY for every node
  distance[start] ← 0
  pending ← MIN_HEAP containing (0, start)

  WHILE pending IS NOT EMPTY
    currentCost, node ← REMOVE_LOWEST(pending)
    IF currentCost > distance[node]
      CONTINUE
    IF node = target
      RETURN currentCost

    FOR EACH edge FROM node
      newCost ← currentCost + edge.weight
      IF newCost < distance[edge.destination]
        distance[edge.destination] ← newCost
        ADD (newCost, edge.destination) TO pending

  RETURN NOT_REACHABLE
```

Suppose a warehouse reaches road A in 10 minutes or road B in 4. B reaches A in 3 more minutes, and A reaches the customer in 5. Dijkstra first records A at 10 and B at 4. Processing B improves A to 7; processing A reaches the customer at 12. The route with more roads wins because its total time is lower.

</TechDepth>

The product requirement selects the traversal. "Fewest introductions" calls for BFS; "can any permission path reach this document?" can use DFS; "run setup before migration" needs topological ordering; "lowest travel time" needs Dijkstra's algorithm.

**Product decision**

- **Used in:** document permissions, social connections, delivery routes, workflow dependencies, recommendations, and fraud-ring investigation.
- **Prefer BFS when:** every relationship has equal cost and the feature needs the fewest hops.
- **Prefer DFS when:** the feature must explore a complete branch, detect a cycle, or visit every reachable item.
- **Prefer topological sort when:** work has one-way prerequisites and the product needs a valid execution order.
- **Prefer Dijkstra's algorithm when:** relationships have non-negative costs and the product needs the lowest total cost; basic BFS or DFS cannot account for those weights.

### Working with text and flags

The first three algorithms here find an exact phrase inside a longer text; they differ in how much repeated comparison they avoid. The fourth is unrelated to text and stores several yes-or-no settings inside one number. A [trie](#trie) covers the remaining text case, matching by prefix while a customer types.

**String matching** finds one sequence of characters inside another. Checking each possible starting position character by character can cost O(n × m), where `n` is the long text length and `m` is the search phrase length.

For matching text, slide a transparent stencil containing the target word across a page. At each position, check whether every letter lines up. A smarter method uses what already matched to decide how far the stencil can move after a mismatch.

#### Direct string matching

Direct matching tries the pattern at each possible starting position. It suits short text where a small, easy-to-check implementation matters more than avoiding every repeated comparison.

<TechDepth>

A direct implementation uses one loop for starting positions and another for characters:

```text
FUNCTION FIND_TEXT(text, pattern)
  IF pattern IS EMPTY
    RETURN 0

  FOR start FROM 0 TO LENGTH(text) - LENGTH(pattern)
    matched ← TRUE

    FOR offset FROM 0 TO LENGTH(pattern) - 1
      IF text[start + offset] ≠ pattern[offset]
        matched ← FALSE
        STOP INNER LOOP

    IF matched
      RETURN start

  RETURN NOT_FOUND
```

Searching `"catalog"` for `"log"` tests starts at `c`, `a`, `t`, and `a` before the characters at `l`, `o`, and `g` all match. This implementation is easy to verify and works well for short text. Repeated partial matches can make it compare the same characters many times.

</TechDepth>

#### Knuth-Morris-Pratt

**Knuth-Morris-Pratt (KMP)** records how much of the pattern remains useful after a mismatch. A **fallback table** stores, for every pattern position, the length of the longest beginning of the pattern that also matches its ending up to that point.

<TechDepth>

For the pattern `"abab"`, the fallback table is `[0, 0, 1, 2]`:

- after `"aba"`, the ending `"a"` matches the beginning `"a"`, so the stored length is 1
- after `"abab"`, the ending `"ab"` matches the beginning `"ab"`, so the stored length is 2

```text
FUNCTION BUILD_FALLBACK(pattern)
  fallback ← ARRAY OF LENGTH(pattern) ZEROS
  matched ← 0

  FOR position FROM 1 TO LENGTH(pattern) - 1
    WHILE matched > 0 AND pattern[position] ≠ pattern[matched]
      matched ← fallback[matched - 1]

    IF pattern[position] = pattern[matched]
      matched ← matched + 1

    fallback[position] ← matched

  RETURN fallback

FUNCTION KMP_FIND(text, pattern)
  IF pattern IS EMPTY
    RETURN 0

  fallback ← BUILD_FALLBACK(pattern)
  matched ← 0

  FOR position FROM 0 TO LENGTH(text) - 1
    WHILE matched > 0 AND text[position] ≠ pattern[matched]
      matched ← fallback[matched - 1]

    IF text[position] = pattern[matched]
      matched ← matched + 1

    IF matched = LENGTH(pattern)
      RETURN position - LENGTH(pattern) + 1

  RETURN NOT_FOUND
```

Searching `"abacabab"` for `"abab"` first matches `"aba"` and then meets `c` instead of `b`. The fallback table says one matched `a` still helps, so the search keeps that progress instead of restarting from the next text position. Building the table and scanning the text take O(m + n) work.

</TechDepth>

#### Rolling hash

A **rolling hash** turns each fixed-length text window into a numeric fingerprint. Moving the window updates that fingerprint instead of recalculating it from every character.

<TechDepth>

`NUMBER(character)` gives each character a number. `MODULO` keeps the fingerprint within a fixed range by taking the remainder after division.

```text
FUNCTION ROLLING_HASH_FIND(text, pattern)
  IF pattern IS EMPTY
    RETURN 0
  IF LENGTH(pattern) > LENGTH(text)
    RETURN NOT_FOUND

  windowLength ← LENGTH(pattern)
  base ← 257
  modulus ← A LARGE PRIME NUMBER
  highestPlace ← base RAISED TO (windowLength - 1), MODULO modulus
  patternHash ← 0
  windowHash ← 0

  FOR offset FROM 0 TO windowLength - 1
    patternHash ← (patternHash × base + NUMBER(pattern[offset]))
                  MODULO modulus
    windowHash ← (windowHash × base + NUMBER(text[offset]))
                 MODULO modulus

  FOR start FROM 0 TO LENGTH(text) - windowLength
    IF windowHash = patternHash
       AND text window at start = pattern
      RETURN start

    IF another window exists
      leadingValue ← NUMBER(text[start]) × highestPlace
      windowHash ← (windowHash - leadingValue) MODULO modulus
      windowHash ← (windowHash × base
                    + NUMBER(text[start + windowLength]))
                   MODULO modulus

  RETURN NOT_FOUND
```

For `"catalog"` and a three-character pattern, the windows are `"cat"`, `"ata"`, `"tal"`, `"alo"`, and `"log"`. Each move reuses the previous fingerprint. Two different windows can share a fingerprint, a **hash collision**, so the algorithm confirms the characters before returning a match.

</TechDepth>

Brand monitoring can use KMP or rolling hashes to scan millions of posts for exact protected names. KMP gives one pattern a dependable linear scan. Rolling hashes help compare many windows or several patterns, with character verification protecting correctness.

#### Bit manipulation

**Bit manipulation** works directly with binary digits, where each **bit** is `0` or `1`. A **bitmask** assigns a meaning to each position, such as read, edit, share, or delete permission. Several yes/no settings then fit inside one number.

For bits, picture a row of light switches on a panel. Each switch represents one permission. Up means allowed (`1`); down means denied (`0`). Reading the panel reveals several yes/no settings at once.

Assign `read = 1`, `edit = 2`, `share = 4`, and `delete = 8`. A customer with read and share permissions has `flags = 1 + 4 = 5`, written as binary `0101`.

<TechDepth>

```text
FUNCTION HAS_PERMISSION(flags, permissionBit)
  RETURN (flags BITWISE_AND permissionBit) ≠ 0

FUNCTION GRANT_PERMISSION(flags, permissionBit)
  RETURN flags BITWISE_OR permissionBit

FUNCTION REVOKE_PERMISSION(flags, permissionBit)
  RETURN flags BITWISE_AND (BITWISE_NOT permissionBit)
```

`HAS_PERMISSION(5, 4)` returns true because both numbers have the share position switched on. Granting edit changes `0101` to `0111`, or 7. Revoking share changes `0111` to `0011`, or 3. Each operation changes or checks one named switch without inspecting the others.

</TechDepth>

Compact storage can help at large volume, but a bitmask is harder to inspect than named fields. Prefer clear names unless storage volume or an interface close to the computer hardware makes the compact form valuable.

**Product decision**

- **Use advanced string matching when:** the product scans large text collections for exact phrases and a character-by-character restart costs too much.
- **Avoid it when:** the collection is small or customers expect matches by meaning, synonyms, or spelling similarity; a full-text or meaning-based search system addresses a different need.
- **Prefer bitmasks when:** the set of yes/no flags is small, stable, and processed at high volume or across a hardware-facing interface.
- **Avoid bitmasks when:** flags change frequently, non-engineers must inspect them, or readability matters more than saving a few bytes.

## Structures on disk

The structures above assume the program can reach data in **memory**, also called RAM, while it runs. RAM is fast but temporary: its contents disappear when the machine loses power. Products therefore keep important records on **disk**, persistent storage that survives a restart but takes longer to read and write.

A **database** organizes persistent records and provides operations for reading and changing them. In a table-shaped database:

- a **row** represents one record, such as one customer
- a **column** or **field** represents one property, such as email
- a **query** asks the database to return or change particular records

Consider a customer signing in with `anadi@example.com`. Without an **index** on the email field, the database may inspect each customer row until it finds a match. That operation is a **full scan**, and its work grows with the number of customers.

An index is a separate data structure that maps searchable values to the records containing them. It works like the index at the back of a book: find the term first, then jump to the relevant page instead of reading every page.

Database indexing applies the same key-to-location idea. Hash maps serve a broader set of jobs, including profiles, caches, counters, sessions, and duplicate detection. A database may choose a **hash index** for exact lookups such as `user_id = 123`, or a **B-tree index** when it also needs values in order or ranges such as accounts created between Monday and Friday.

<IndexVsScanDiagram />

An index creates a trade-off:

- Reads using the indexed field become faster.
- The index occupies additional disk space.
- Every inserted or updated record may also require an index update.
- An index on the wrong field consumes resources without helping an important customer path.

The product question is not "Can we add an index?" It is "Which customer action needs this query to stay fast as records grow?"

<LsmVsBtreeDiagram />

Martin Kleppmann's *Designing Data-Intensive Applications* explains four useful storage shapes:

- **Hash-index model:** a coat-check ticket maps one claim number to one hook. Staff jump to that hook without searching every coat, but the ticket numbers do not help them retrieve coats checked between two times.
- **LSM-tree model:** a mailroom accepts new letters into a small sorted tray, periodically files that tray as one sorted bundle, then merges bundles during quieter periods.
- **B-tree model:** a filing cabinet uses labelled guide cards. Each guide sends you to a smaller range of folders until you reach the page containing the requested key.
- **Column-storage model:** instead of keeping each person's complete form together, keep all ages in one cabinet, all countries in another, and all purchase totals in a third. An analytics question reading only country and total avoids opening unrelated fields.

| Storage structure | How it organizes data | Suitable product workload | Cost to remember |
|---|---|---|---|
| Hash index | Keep a map from each key to the location of its record on disk. | Exact lookups such as session ID to session, when the complete key map fits in memory. | It does not naturally support sorted ranges such as "orders between Monday and Friday." |
| Log-structured merge tree (LSM tree) | Accept writes in memory, save them into **Sorted String Tables (SSTables)**, files whose records are ordered by key, then merge those files later. | Write-heavy products such as event collection, logs, and measurements recorded over time. | Background merging, called **compaction**, consumes processor and disk capacity and can slow reads. |
| B-tree | Store sorted keys in fixed-size disk blocks called **pages**, arranged as a balanced tree. | Mixed reading and writing, including queries for values between two boundaries, in many table-based relational databases. | Updating pages creates writes at different disk locations and needs recovery protection if the machine crashes. |
| Column-oriented storage | Store values from the same column together instead of keeping each complete row together. | Analytics that scans a few fields across millions of events, such as total revenue by country. | Reconstructing one complete record can require reading from several column locations. |

For another example, consider payment retries the way Stripe-style systems handle them. A phone loses its connection after sending a payment request, and the customer retries because the product did not show a result. If the server treats that retry as a new purchase, it charges the customer twice. The client therefore sends an **idempotency key**, a unique label identifying that payment attempt. The server stores the result under that key. A retry with the same key returns the original result instead of creating another charge. An index makes the key lookup fast enough to run before every payment action.

<TechDepth>

**Why LSM trees suit writes.** The database first writes into a sorted in-memory structure. When that structure fills, it saves the whole sorted block to disk in one sequential operation. Sequential writes are efficient, but the database must later merge several files and remove overwritten values. That compaction work competes with customer queries for disk capacity.

**Why B-trees suit ranges.** Each page contains sorted keys and pointers to child pages. A query such as "orders between these two dates" navigates to the first matching page, then walks nearby pages in order. A **write-ahead log** records an intended change before modifying the B-tree, allowing the database to recover if a crash interrupts the update.

**Primary and secondary indexes.** A primary index usually follows the record's main identity, such as customer ID. A secondary index supports another lookup, such as email or creation date. Each additional index makes selected reads faster while adding storage and write work.

**Compression** stores repeated values using fewer bytes. Column stores compress well because adjacent values often share a type or repeat. That is one reason analytics systems can scan selected columns across billions of rows efficiently.

</TechDepth>

## Choosing search machinery

**Searching** means locating one or more matching items. The algorithms and indexes above each handle part of the job, so a search requirement becomes a choice between four levels of machinery.

Lesson search shows why the promise matters. It could support exact titles, the beginning of a title, spelling mistakes, synonyms, or results based on meaning rather than matching words. Each promise needs different machinery.

| Approach | What it does | Suitable when | Limitation |
|---|---|---|---|
| Linear scan | Check each title until a match appears. | The catalog contains only dozens of lessons. | Work grows with every item and repeats for every search. |
| Binary search | Compare with the middle of a sorted list and discard half after each step. | Data is sorted and the customer expects an exact value. | It does not handle spelling mistakes or relevance ranking by itself. |
| Database index | Maintain a separate lookup structure for a field such as a page identifier or email address. | The application repeatedly searches the same field. | The index consumes storage and adds work whenever records change. |
| Full-text search | Build a word-to-document lookup, then rank matching documents. | Customers expect partial text, relevance, or language-aware matching. | The team must operate a larger search system and own its ranking rules. |

Before choosing technology, state:

- how many items customers will search
- whether spelling mistakes should still match
- whether exact, prefix, or meaning-based results are required
- how quickly new content must appear in results
- whether search is central to activation or a rarely used convenience

<TechDepth>

**Full-text search** builds an **inverted index**, a map from each term to the documents containing it. A ranking formula then orders matches. Recency, popularity, personalization, and exact-match weighting are product choices expressed as numbers.

</TechDepth>

## Taking this into the room

The remaining sections turn the material into working habits: what to specify, what to spend, how to brief engineering, what this site already does, and how to practise.

### Correctness is a product surface

An **edge case** is a valid but unusual input near the boundary of normal use. Algorithms often look correct on average examples and fail at those boundaries.

A cart discount calculated from a list of line items shows how boundaries become product decisions. The specification must answer:

- **Empty cart:** should the total be zero, or should checkout be blocked?
- **One item:** does a bundle discount require at least two items?
- **Duplicate item:** should two units appear as two rows or one row with quantity two?
- **Zero or negative price:** can a credit create a negative total?
- **Maximum size:** what happens when a wholesale customer imports 100,000 lines?
- **Concurrent edit:** which result wins if two employees change the same order at once?

Text adds another set of boundaries: capital letters, surrounding spaces, accents, emoji, and writing systems where one visible character uses several code units. Dates add time zones and daylight-saving transitions.

These are product decisions. Writing them into the specification prevents an engineer from guessing and a customer from discovering the guess through lost data, a wrong charge, or a support ticket.

### Cost, and what "good enough" means

The fastest technical design is not automatically the best product decision. A small catalog may not justify a dedicated search system. "Good enough" means the simplest approach that meets the current customer promise and has a named threshold for replacement.

| Choice | Customer experience | Operating cost | Delivery cost | Suitable stage |
|---|---|---|---|---|
| Scan every item on each request | Response time grows as the catalog grows. Customers eventually wait longer for the same action. | Repeated scans consume database and processor capacity on every request. | Engineers can build and understand it quickly. | Early product with small, bounded data and low traffic. |
| Keep a temporary copy of popular results | Repeated requests return quickly, but customers may briefly see an older answer. | Memory costs money, and the team must decide when to refresh or remove stale copies. | Engineers must add cache updates, monitoring, and fallback behaviour. | Growing product with repeated reads of the same results. |
| Operate a dedicated search or ranking service | Search can support spelling tolerance, relevance, and predictable speed at large scale. | The service has a fixed bill and needs monitoring even during quiet periods. | Engineers must copy record changes into the search service and own ranking quality. | Search is a central customer journey and simpler approaches miss its target. |

A useful search brief makes each trade-off explicit:

- **Outcome:** customers who find a lesson are more likely to start one.
- **Scale:** the catalog contains 50,000 lessons and receives 50,000 searches per day.
- **Latency target:** 95% of searches return within 300 milliseconds. This is called **p95 latency**.
- **Freshness:** a new lesson may take up to one hour to appear.
- **Appetite:** the team can spend one engineering week before reconsidering scope.

"Make it faster" omits the information engineering needs to choose an approach.

### Brief engineering with seven answers

A product brief for algorithmic work should answer seven questions:

1. **User job:** what is the customer trying to finish?
2. **Outcome metric:** which measurable behaviour changes if the feature improves?
3. **Input size:** what does `n` represent, how large is it today, and how large could it become?
4. **Latency target:** how long may the action take, including a percentile such as p95 rather than an average that hides slow requests?
5. **Freshness:** must the answer reflect changes immediately, or can it update hourly or nightly?
6. **Appetite:** how many engineering days is this outcome worth before the team reduces scope?
7. **Fallback:** what does the customer see if the faster or more accurate path is unavailable?

### Specimen: this Learn site

The Learn product provides a final example. It already uses several structures even though the traffic is small:

| Feature | Structure or pattern | Why it fits | Product outcome |
|---|---|---|---|
| Lessons within a track | An ordered array keeps lesson one before lesson two. | The interface renders a short sequence and often moves to the next position. | A clear sequence helps a reader continue instead of deciding where to go next. |
| Lesson page identified by its URL slug | A keyed lookup maps a **slug**, the short text identifying a page in its web address, such as `cs-fundamentals`, to one lesson. | The page URL already provides the key, so scanning all lessons would waste work. | The requested page resolves quickly and reliably. |
| Sidebar table of contents | A tree represents headings and their nested subheadings. | Parent and child headings already form a hierarchy. | Readers can understand and navigate a long lesson. |
| Quiz answer check | A map connects each answer ID to its label and correctness. | The selected ID directly identifies the answer record. | Feedback appears immediately after selection. |
| Waitlist signup | A normalized email plus a uniqueness check behaves like a set. | Membership answers whether that address already exists. | The demand count does not include accidental duplicates. |
| Future trending-lessons list | A heap can retain the lessons with the highest start counts. | The page needs only the top few lessons rather than a complete ranking. | Readers find popular material without recalculating every position. |
| Future lesson search | An inverted index maps words to lessons containing them. | Readers search by terms rather than exact lesson IDs. | Search can move a reader from intent to a lesson start. |

Current traffic and catalog size make simple implementations appropriate. The brief should still name the threshold that would justify a more complex structure, such as search response time exceeding 300 milliseconds after the catalog reaches 50,000 lessons.
